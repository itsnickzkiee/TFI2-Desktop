# TFI Audit Trail — UI Specification v0.1

**Date:** 18 November 2026  
**Project:** TFI_NEW  
**Screen:** Audit Trail  
**Current status (20 November 2026):** Verified UI preview; no sample events displayed; live audit capture not connected

## 1. Purpose

Audit Trail provides administrators with a read-only record of important user actions and system events across TFI. It supports accountability, traceability, incident review, and verification of changes made to operational records and reference data.

The screen is an activity viewer. It is not an editing workspace and must not provide actions to alter or delete audit records.

## 2. Screen contents

- TFI-branded sidebar with Audit Trail selected under Administration.
- Breadcrumb: TFI / Administration / Audit Trail.
- Summary cards for matching events, data changes, import activities, and access/security activities.
- Activity filters: All Activity, Data Changes, Imports, Access & Security, and System Events.
- Search by user, action, module, record reference, summary, or event ID.
- Module filter and date-range filter.
- Activity table with timestamp, actor, activity, module, record reference, change summary, event type, and details action.
- Read-only event details modal.
- CSV export for the currently filtered event list.
- Clear indication that audit capture is not connected; no sample, mock, or fabricated events are shown.

## 3. Event types

**Data changes**
- Create, update, and approved reference changes.
- Capture the affected module and record reference.
- Where appropriate, capture the previous and new values for changed fields.

**Import activities**
- Workbook selected, scan started, scan completed, import staged, import confirmed, and import completed or failed.
- Link events to the import batch and source workbook.
- Record inserted, incomplete, duplicate-skipped, held, and failed row totals where applicable.
- Preserve the rule that incomplete operational records may still be inserted when permitted; existing duplicate records must not be inserted again.

**Access and security**
- Successful and unsuccessful sign-ins, sign-outs, role changes, permission changes, and account status changes.
- Never store passwords, access tokens, session secrets, or other authentication credentials in audit details.

**System events**
- Scheduled reference refreshes, validation outcomes, and other important automated processes.
- Identify the responsible service or background process rather than attributing automated work to a human user.

## 4. Event data requirements

Each production audit event should retain, where applicable:
- Immutable event ID.
- Server-generated timestamp in a consistent timezone.
- Actor user ID and display-name snapshot.
- Actor role snapshot at the time of the event.
- Action name and event category.
- Target module, entity type, and record reference.
- Source screen or process.
- Outcome / result.
- Previous and new values for approved auditable fields.
- Related import batch ID or correlation ID where applicable.
- Safe description for human review.

Sensitive values must be excluded or redacted. Audit events must not store passwords, access tokens, private keys, or other authentication secrets. Full record payloads should not be copied into the audit log when a concise field-level change is sufficient.

## 5. Behavior and controls

- Search and filters operate on the visible audit event set.
- Event details open in a read-only modal.
- CSV export contains only the currently filtered events.
- No Add, Edit, Delete, Clear, or overwrite action is available.
- New audit events are generated by trusted server-side operations, not by client-side UI code.
- The actor and timestamp must be assigned by the trusted service; they must not be accepted as authoritative values from the browser.
- Audit records remain available even if the referenced operational record is later changed or removed.
- Access to audit events and export must be authorized server-side.

## 6. Current prototype boundary

- audit-trail-preview.html is a local visual and interaction prototype.
- The event collection starts empty; no sample, mock, or fabricated audit events are embedded in the page or a data file.
- With no verified events, all four summary metrics display a neutral dash, the table shows the no-records state, and CSV export remains disabled.
- Search, category tabs, module filters, date filters, and the read-only event details modal are implemented for verified records supplied by a future trusted source.
- The CSV export action operates only on the currently filtered verified event set and remains unavailable while that set is empty.
- The browser-only test fixture used to verify event details is injected temporarily during automated tests and cleared immediately; it is not stored in the preview or any persistent data source.
- No live database reads or writes occur.
- No actual user activity is being monitored or recorded by this prototype.

## 7. Production requirements

The live Audit Trail must:
- Receive events from trusted server-side application workflows.
- Use an append-only event model.
- Enforce read permissions and export permissions independently of UI visibility.
- Preserve event IDs, actor snapshots, timestamps, event categories, target references, and approved change details.
- Link spreadsheet scan and import events to their source workbook and batch identifiers.
- Log successful and failed attempts where relevant to security and traceability.
- Avoid logging secrets and unnecessary personal information.
- Define an approved retention and archival policy with the client.
- Prevent ordinary users and administrators from editing or deleting existing audit events through the application.

## 9. Acceptance audit and UI refinements — 20 November 2026

The Audit Trail preview was reviewed and refined through the shared TFI dashboard shell.

### Refinements
- Renamed the first metric from "Events in sample" to **Matching events**, reflecting the active filters and the no-mock-data rule.
- Expanded the module filter to cover the operational modules, import/report destinations, all nine Master Data reference categories, administration, authentication, and Dashboard.
- Added accessible tab semantics: tab roles, selected state, tab-panel relationship, and keyboard navigation using Left/Right Arrow, Home, and End.
- Improved search so terms entered in the local event search and global search can match across the event's searchable fields independently.
- Removed the static page-one control from the empty state; pagination remains hidden until verified event records exist.
- Kept the page read-only, with no add/edit/delete/clear/restore actions.
- Kept CSV export disabled while there are no verified events.
- Preserved the explicit notice that audit capture is not connected and that no sample events are shown.

### Browser acceptance tests
Passed checks:
- Audit Trail opens through the shared dashboard router and is selected in the persistent sidebar.
- Empty state contains no fabricated event rows; all four metrics remain neutral.
- All five activity category tabs respond and expose correct accessible selected state.
- Keyboard tab navigation works with arrow keys.
- Module filter contains 36 choices, including all operational modules and Master Data.
- Multi-term search, module filtering, and date filtering execute without errors.
- A temporary browser-memory-only test fixture verified the read-only details modal, previous/new state display, and Escape-key close. The fixture was cleared immediately after the test and is not stored in the HTML or a data file.
- No CRUD controls are exposed.
- Export remains disabled after the test fixture is cleared.
- Audit Trail → Users & Access → Audit Trail navigation returns to the correct module.
- At a 390px outer viewport, the embedded page has no page-level horizontal overflow and the wide audit table scrolls within its own container.
- No browser page errors, console errors, or failed local asset requests were detected.
